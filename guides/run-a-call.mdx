---
title: "Run a call from your own page"
description: "Open the audio connection, then read the answers as they arrive."
---

There is no endpoint that says "start a call". A call starts when a browser opens an
audio connection to the server. Three steps.

## 1. Invent a conversation id

You choose it, not the server. In a browser, `crypto.randomUUID()` does the job. It only
has to be unique for that agent. Everything the call produces is filed under this id.

```js
const conversationId = crypto.randomUUID();
```

## 2. Post a WebRTC offer to /offer

`/offer` is not under `/api/v1`. It is at the bare path on the same server, for example
`http://localhost:7860/offer`.

The body is the offer your WebRTC code produced, plus a `request_data` object naming the
agent and the conversation id you just made up.

```json
{
  "sdp": "v=0\r\no=- ...",
  "type": "offer",
  "request_data": {
    "agentId": "a87c1556-79fa-4492-add9-a704c13466a3",
    "conversation_id": "6f1f0a1c-1111-4b0c-9a3a-2b6f9c0d0001"
  }
}
```

The reply is the WebRTC answer. Apply it and the agent starts talking. Send ICE
candidates to the same path with `PATCH /offer`, carrying `pc_id` and `candidates`.

The practical way to do the WebRTC part is a browser client library that handles it for
you, rather than writing the signalling by hand.

## 3. Read the answers as they arrive

Call `GET /api/v1/data/{agent_id}/{conversation_id}` on a timer while the call is
running. Every two seconds is a reasonable rate.

```bash
curl "$FORMBHARO_URL/api/v1/data/a87c1556-79fa-4492-add9-a704c13466a3/6f1f0a1c-1111-4b0c-9a3a-2b6f9c0d0001"
```

```json
{
  "form_data": {
    "consent": true,
    "full_name": "Asha Rao",
    "has_fever": "Yes",
    "phone": null
  },
  "form_status": {
    "consent": "answered",
    "full_name": "answered",
    "phone": "skipped",
    "has_fever": "answered",
    "fever_started_on": "empty",
    "fever_symptoms": "empty"
  }
}
```

Before the first answer is saved the whole reply is `{}`. See
[Answers](/concepts/answers).

## Drawing the form on your page

`GET /api/v1/agents/{agent_id}/public` gives you the agent's title and its questions,
which is what a page needs to show the form filling in as the person talks.

```bash
curl "$FORMBHARO_URL/api/v1/agents/a87c1556-79fa-4492-add9-a704c13466a3/public"
```

```json
{
  "id": "a87c1556-79fa-4492-add9-a704c13466a3",
  "title": "Clinic intake",
  "questions": [
    {
      "name": "full_name",
      "label": "What is your full name?",
      "type": "string",
      "required": true
    }
  ],
  "agent_speaks_first": true
}
```

## These routes take no key

There is no `Authorization` header in the two commands above. That is not an omission.

`POST /offer`, `GET /api/v1/data/{agent_id}/{conversation_id}`,
`GET /api/v1/agents/{agent_id}/public`, and
`PATCH /api/v1/agents/{agent_id}/conversations/{conversation_id}/form_data` all accept
requests with no key at all. Your page runs in someone's browser, where a key could be
read by anyone, so these four do without one.

<Warning>
Anyone who knows an agent id can read a live call's answers and can overwrite them. The
agent id is a random identifier and is not published anywhere, so it is the only thing
standing between a stranger and that call's answers. If your agents collect anything
sensitive, put your own check in front of these routes before you open your server to the
internet.
</Warning>
