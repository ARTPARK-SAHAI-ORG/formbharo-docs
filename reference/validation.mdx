You can attach a `validation` object to any question to enforce the format of the answer. Validation runs in two places: during the call (triggering a retry if the answer doesn't match), and when you manually correct an answer via `PATCH /api/v1/agents/{agent_id}/conversations/{conversation_id}/form_data`.

## Validation object structure

Add a `validation` key to any question object and set its `type` to one of the rule names below. Some rules accept additional parameters in a `rules` sub-object.

```json
{
  "validation": {
    "type": "<rule-name>",
    "rules": { ... }
  }
}
```

For rules that take no parameters (such as `date`), you can omit `rules` entirely.

## Available rules

<Accordion title="phone_number — 10-digit Indian phone number">
  Validates that the answer is a 10-digit Indian mobile or landline number.

  **Parameters:**

  | Key | Type | Description |
  |---|---|---|
  | `digits` | integer | The required digit count. Pass `10` for standard Indian numbers. |

  **Behaviour:**
  - Strips leading `+91`, `91`, or `0` prefixes before counting digits.
  - Rejects numbers where all digits are the same (e.g., `9999999999`).

  ```json
  {
    "validation": {
      "type": "phone_number",
      "rules": { "digits": 10 }
    }
  }
  ```
</Accordion>

<Accordion title="min_length — minimum character count">
  Requires the answer to be at least a given number of characters long.

  **Parameters:**

  | Key | Type | Description |
  |---|---|---|
  | `min_length` | integer | The minimum number of characters required. |

  ```json
  {
    "validation": {
      "type": "min_length",
      "rules": { "min_length": 5 }
    }
  }
  ```
</Accordion>

<Accordion title="exact_num_digits — exact digit count">
  Requires the answer to contain exactly the specified number of digits, ignoring non-digit characters.

  **Parameters:**

  | Key | Type | Description |
  |---|---|---|
  | `digits` | integer | The exact number of digits required. |

  ```json
  {
    "validation": {
      "type": "exact_num_digits",
      "rules": { "digits": 6 }
    }
  }
  ```
</Accordion>

<Accordion title="number_range — numeric range">
  Requires the numeric answer to fall within a specified range. You can supply one or both bounds.

  **Parameters:**

  | Key | Type | Description |
  |---|---|---|
  | `min` | number | The minimum allowed value (inclusive). Optional. |
  | `max` | number | The maximum allowed value (inclusive). Optional. |

  ```json
  {
    "validation": {
      "type": "number_range",
      "rules": { "min": 0, "max": 120 }
    }
  }
  ```
</Accordion>

<Accordion title="date — valid DD-MM-YYYY date">
  Requires the answer to be a valid calendar date in `DD-MM-YYYY` format.

  **Parameters:** None.

  ```json
  {
    "validation": {
      "type": "date"
    }
  }
  ```
</Accordion>

<Accordion title="date_format — alias for date">
  An alias for the `date` rule. Behaves identically — use whichever name feels clearer in your configuration.

  **Parameters:** None.

  ```json
  {
    "validation": {
      "type": "date_format"
    }
  }
  ```
</Accordion>

<Accordion title="date_today_or_past — today or earlier">
  Requires the answer to be a valid `DD-MM-YYYY` date that is today or in the past. Useful for fields like date of birth or symptom onset date.

  **Parameters:** None.

  ```json
  {
    "validation": {
      "type": "date_today_or_past"
    }
  }
  ```
</Accordion>

<Accordion title="date_future — strictly after today">
  Requires the answer to be a valid `DD-MM-YYYY` date that is after today. Useful for appointment or follow-up dates.

  **Parameters:** None.

  ```json
  {
    "validation": {
      "type": "date_future"
    }
  }
  ```
</Accordion>

<Accordion title="regex — custom regular expression">
  Validates the answer against a regular expression you define. Include a `message` to tell the agent (and the caller) what format is expected.

  **Parameters:**

  | Key | Type | Description |
  |---|---|---|
  | `pattern` | string | A valid regular expression. |
  | `message` | string | A human-readable error message shown when the pattern does not match. |

  ```json
  {
    "validation": {
      "type": "regex",
      "rules": {
        "pattern": "^[A-Z]{2}[0-9]{6}$",
        "message": "Must be two capital letters followed by six digits"
      }
    }
  }
  ```
</Accordion>

<Accordion title="free_text — natural-language LLM rule">
  Describes a validation rule in plain English, enforced by the LLM during the call. Use this for rules that are difficult to express as a pattern — for example, requiring a valid Indian state name.

  **Parameters:**

  | Key | Type | Description |
  |---|---|---|
  | `description` | string | A plain-language description of what constitutes a valid answer. |

  ```json
  {
    "validation": {
      "type": "free_text",
      "rules": { "description": "Must be a valid Indian state name" }
    }
  }
  ```

  <Warning>
    The `free_text` rule is only enforced during the live call. It is **not** checked when you manually patch form data via `PATCH /api/v1/.../form_data`. Use a `regex` or other structural rule if you need server-side enforcement on manual edits.
  </Warning>
</Accordion>

## Failure response

When validation fails during a `PATCH /api/v1/agents/{agent_id}/conversations/{conversation_id}/form_data` request, you receive HTTP `400`. The response body identifies every field that failed:

```json
{
  "error": "Validation failed",
  "invalid_fields": {
    "phone": {
      "value": "999",
      "normalized_value": "999",
      "error": "Must be 10 digits",
      "source": "phone_number"
    }
  }
}
```

<ResponseField name="invalid_fields" type="object">
  A map of field names to failure details. Each entry describes one field that failed validation.

  <Expandable title="Fields in each invalid_fields entry">
    <ResponseField name="value" type="any">
      The raw value you submitted.
    </ResponseField>
    <ResponseField name="normalized_value" type="any">
      The value after any pre-processing (e.g., stripping a country code prefix from a phone number). This is the value the rule actually tested.
    </ResponseField>
    <ResponseField name="error" type="string">
      A human-readable explanation of why the value failed.
    </ResponseField>
    <ResponseField name="source" type="string">
      The rule type that rejected the value — e.g., `"phone_number"` or `"number_range"`.
    </ResponseField>
  </Expandable>
</ResponseField>

<Note>
  Nothing is saved if any field fails validation. Fix all reported fields and resubmit the entire patch.
</Note>
